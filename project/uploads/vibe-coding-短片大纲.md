# Vibe Coding 需要注意的细节：动画短片大纲

> 用途：给另一个会话制作动画短片用的章节级大纲。内容、数据、画面构思在这里定好；分镜、字幕全文、视觉风格由制作会话完成。
> 信息截至 2026 年 10 月。

---

## 一、制作说明

**观众**：Java 初学实验课的同学。刚装好 JDK、IDEA、Git 和 Qoder 插件，写过 Hello World，大多没用过 Agent。

**播放方式**：课上播放（老师会在章节之间暂停补充），课后也会自己看。所以旁白字幕要完整，不靠讲解也能看懂。

**时长**：约 10 分钟。片头 + 9 章 + 片尾清单。每章都要能单独播放。

**字幕量**：中文字幕按每秒 4–5 个字的阅读速度估算，每章旁白约 250–350 字。超出就删要点，不要压缩阅读时间。

**播放器功能**：
- 自动播放、暂停/继续、进度条（标出章节位置）、按章节跳转、全屏、播完可重播；
- 要在投影仪上看清，字幕字号要大；
- 数据的出处用小字标在画面角落（机构 + 年份即可）。

**文风要求**（重要）：
- 平实陈述，像教材，不像宣传片；
- 标题直接写这一章讲什么，不用"X：Y"式标题，不用口号、排比、反问；
- 结尾不总结、不升华；
- 英文术语第一次出现时给一句中文解释；
- 所有数字必须带来源和年份，不要自己补数字；
- 不写具体模型的版本号排名，因为一个月就过时。

**和课件的衔接**：课件第五章已经讲过 Qoder 的安装、对话面板、三种模式，以及"使用 AI 的注意事项"五条：
1. 不发密码、Token、私钥和他人的个人信息；
2. 检查 diff；
3. 运行并通过测试后再提交；
4. AI 生成的部分要能解释清楚；
5. 每次提交只包含一项改动。

本片不重复安装和界面操作，讲的是这些规则背后的原因和更多细节。上面五条在片中提到时一句带过即可。

### 第 1 章　什么是 vibe coding（35 秒）

**要点**
1. 2025 年 2 月，Andrej Karpathy（OpenAI 联合创始人之一）发帖提出 vibe coding：完全顺着感觉走，忘掉代码的存在。他在同一条帖子里也说，这种方式用在周末随手做、用完就扔的小项目上还行。
2. 2025 年 11 月，柯林斯词典把 vibe coding 选为年度词。
3. Simon Willison 的区分：代码是 AI 写的，但你审过、充分测试过、能给别人讲清楚它怎么工作，这就不算 vibe coding，而是正常的软件开发。
4. 引出全片主线：项目可以排在一条轴上。左端是用完就扔的小玩具，右端是要交的作业、给别人用的程序、要上线的服务。越往右，后面各章的内容越重要。

**画面构思**
- Karpathy 原帖的英文原句打字出现，下方给中文翻译。
- 一条横轴和一个滑块，滑块从左往右移，右侧逐个亮起"作业""给别人用""上线"。
- 这条轴可以在后面几章里作为回扣元素再次出现。

**原文备用**："There's a new kind of coding I call 'vibe coding', where you fully give in to the vibes, embrace exponentials, and forget that the code even exists."

---

### 第 2 章　AI 写代码时在做什么（50 秒）

**要点**
1. 模型不记得你。每次回答时，它只能看到"上下文窗口"里的内容，包括：
   - 工具的系统设定；
   - 你说的话；
   - 它读过的文件；
   - 命令的输出。
2. 模型的知识停在训练截止日期。之后发布的新版本库它不知道，可能按旧写法写，也可能编一个看起来合理但不存在的方法。
3. 现在的编程助手大多是 Agent（智能体），按一个循环工作：读文件 → 决定下一步 → 调用工具（改文件、跑命令）→ 看结果 → 再决定下一步，直到它认为任务完成。
4. 上下文窗口的容量是有限的，内容越多，模型越容易漏看、搞混。Chroma 2025 年测了 18 个模型，发现输入越长表现越不稳定，简单任务也是如此，这被称为 context rot。窗口满了以后，工具会压缩前面的内容，细节就丢了。
5. 你能控制的有三处，后面按这个顺序讲：
   - 给它什么：提示词和上下文；
   - 用哪个模型；
   - 用什么工具来运行它，也就是 harness。

**画面构思**
- Agent 循环画成一个转动的环，四个节点依次点亮。
- 上下文窗口画成一个容量固定的容器，不同颜色的块（你的话、文件、命令输出）不断堆进去；接近满时，底部的旧块被压扁、变模糊。
- 结尾三个控制点并排出现，作为后面章节的目录。

**来源**：Chroma, *Context Rot*, 2025-07

---

### 第 3 章　提示词（75 秒）

**要点**
1. 以"帮我写个登录功能"为例。这句话没说的事情很多：
   - 密码怎么存？
   - 要不要注册功能？
   - 输错几次锁定？
   - 用 Session 还是 Token？

   每一个没说的地方，AI 都会自己选一种做法，选的不一定是你要的。这就是 garbage in, garbage out 的具体含义。
2. 写清楚的提示词包括五部分：
   - 目标：要做成什么；
   - 背景：项目用什么技术，相关代码在哪；
   - 约束：哪些文件不能改，能不能加新依赖；
   - 验收标准：怎样算完成，怎么验证；
   - 参考：已有的类似代码或示例。

   顺便说明为什么要这样做。Anthropic 的官方提示词指南也建议写出原因，模型能据此做出更贴合的判断。
3. 同一个需求的两种写法并排对比：
   - 模糊：`帮我写个登录功能`
   - 清楚：`在 UserService 里加一个 login(username, password) 方法。密码用项目里已有的 PasswordUtil.verify() 校验。连续输错 5 次锁定 15 分钟。不要修改 User 类的字段，不要加新依赖。写完补 JUnit 测试，覆盖登录成功、密码错误、账号锁定三种情况，并运行通过。`
4. 报错时提供四样东西：完整报错和堆栈、你做了什么操作、期望的结果、实际的结果。界面问题直接贴截图。不要只说"跑不起来"。
5. 大任务拆成小任务，一个对话只做一件事。需求自己还没想清楚时，先让它提问或先给方案，不要直接让它写代码。
6. 有些老技巧已经没必要了：
   - "你是世界顶级程序员"这类身份设定；
   - 全大写的"必须"；
   - 威胁或许诺给小费。

   Anthropic 的官方指南提到，新模型对指令更敏感，过重的语气反而可能让它过度执行，建议用正常语气写。

**画面构思**
- "帮我写个登录功能"作为树根，向下长出决策树。每个分叉是一个没说清的问题，标着"?"；AI 随机走了一条，亮起来的结果和你想要的不一样。
- 换成写清楚的提示词后，分叉一根根被剪掉，最后只剩一条路。
- 五部分（目标、背景、约束、验收、参考）在清楚版提示词上用不同颜色标出来。

**来源**：Anthropic, *Prompting best practices*（platform.claude.com）

### 第 4 章　上下文（60 秒）

**要点**
1. AI 实际看到的内容包括：这次你说的话、之前的对话、它读过的文件、工具的输出、项目规则文件。提示词只是其中一部分。
2. 项目规则文件（AGENTS.md、CLAUDE.md、Qoder 的项目规则等）会在每次对话时自动带上。适合写的内容：
   - 怎么构建；
   - 怎么运行测试；
   - 代码规范；
   - 哪些目录不要动。
3. ETH Zurich 的研究（ICLR 2026）比较了两种规则文件：
   - 让 AI 自动生成的：8 组实验里有 5 组成功率下降，成本增加 20% 以上；
   - 开发者手写的：成功率平均提高约 4%。

   所以规则文件要自己写，写短，只写 AI 从代码里看不出来的内容。
4. 用 @ 指定相关文件，比让它在整个仓库里自己搜更准，也更省。
5. 同一个对话里来回失败几次后，上下文里堆满了错误的尝试，它会被带偏。这时新开一个对话，只把有用的结论带过去。
6. 用到较新的库时，把官方文档的相关段落贴给它，或者接入能查文档的工具。MCP 是让 AI 连接外部工具和数据的一种标准接口，这里只提一句是什么，不讲配置。

**画面构思**
- 上下文容器分层显示：规则文件在最底层，一直都在；对话、文件、输出往上堆。
- 研究数据用两根对比柱表示："AI 生成"向下，"手写"向上，旁边标出成本变化。
- 左边是一个越来越乱的长对话（红色的失败尝试越堆越多），右边是一个干净的新对话，只有一张写着"结论"的卡片被带过去。

**来源**：Gloaguen et al., *Evaluating AGENTS.md*, ETH Zurich / ICLR 2026（arXiv 2602.11988）

### 第 5 章　选模型和费用（70 秒）

**要点**
1. 模型大致分三档：
   - 旗舰：能力最强，也最慢、最贵。适合架构设计、难查的 bug、长时间自主运行的任务。
   - 主力：日常写功能。
   - 轻量：代码补全、改格式、简单重命名。
2. 很多模型可以调整思考强度。难题调高，机械性修改调低，能省时间也省钱。
3. 费用要按"完成一个任务花多少"来算，而不是看每百万 token 的单价，原因有两个：
   - 每一轮对话都会把之前的内容重新发给模型，所以对话越长，每一轮越贵；
   - Agent 做一个任务可能读几十个文件、跑很多轮。

   单价便宜的模型如果多绕几轮，总价反而可能更高。
4. 订阅制有用量上限；按量付费的 API 要设预算提醒。
5. 排行榜只能参考。分数受测试时用的工具影响（第 6 章细讲），公开题目也可能混进了训练数据。最可靠的办法是拿自己的真实任务试两三个模型。
6. 国内可以直接用的有通义千问、智谱 GLM、Kimi、DeepSeek 等，都有面向编程的套餐。只列厂商，不列版本号。
7. 卡住的时候换一个模型再问一次，是正常的排查办法。
8. 免费版本可能会用你的数据训练，要看清设置。课程练习一般不要紧，实习和公司代码按公司规定来。

**画面构思**
- 三档用三张卡片表示，每张标出适合的任务类型。
- 两条计费条赛跑：A 单价低但转了很多圈，B 单价高但两圈就到，最后 A 的总额超过 B。
- 一段对话逐轮变长，每一轮发给模型的内容块随之变大，用来直观说明"对话越长每轮越贵"。

### 第 6 章　Harness（85 秒）

**要点**
1. Harness 指模型之外的全部，包括：
   - 系统提示词；
   - 它能调用的工具：读写文件、执行命令、搜索、浏览器；
   - 权限设置；
   - 上下文管理：压缩、拆给子代理；
   - 规则文件、hooks（在特定时机自动运行的脚本）；
   - 让它自己检查结果的反馈：跑测试、跑代码检查。
2. 打个比方：模型是发动机，harness 是整辆车。同一台发动机装进不同的车，跑出来的成绩不一样。
3. Princeton HAL 团队 2025 年 12 月的测试：同一个 Claude Opus 4.5 做 CORE-Bench，用他们自己的通用框架得分 42%，放进 Claude Code 得分 78%，修正评分错误后是 95%。但换成其他模型，差距小得多，有的模型反而在通用框架里表现更好。所以模型和 harness 要放在一起看，不能只看模型。
4. 常见形态按自主程度从低到高排列：
   1. 行内补全：你打字时帮你补下一段；
   2. 对话面板：问答、解释、生成片段；
   3. IDE 里的 Agent：Qoder、Trae、Cursor、GitHub Copilot 的 Agent 模式；
   4. 命令行 Agent：Claude Code、Codex CLI、Gemini CLI、OpenCode、Qwen Code；
   5. 云端后台 Agent：把任务交给云端，跑完直接提交 PR（合并请求）；
   6. 应用生成平台：Lovable、Bolt、v0 等，一句话生成整个应用，主要面向不写代码的人。

   越往上，你亲自看的代码越少，检查和隔离就越要靠流程来保证。
5. 选工具时看这几项：
   - 在哪写代码：IDE 还是终端；
   - 能用哪些模型，能不能换；
   - 计费方式；
   - 权限控制和撤销功能（检查点）；
   - 是否支持规则文件和 MCP；
   - 国内网络能否直接用；
   - 数据会不会被拿去训练。
6. 给这门课的建议：先用 IDEA 里的 Qoder；熟悉 Git 和命令行之后，再试命令行 Agent；应用生成平台只拿来做原型。
7. 应用生成平台的一个反面例子：2026 年 5 月，RedAccess 扫描了约 38 万个用 Lovable、Base44、Replit 等平台生成并公开访问的应用，约 5000 个暴露了敏感数据，包括病历、银行记录、客服对话。主要原因是这些平台默认公开，用户没有改成私有。
8. 不要让几个 Agent 同时修改同一个仓库里的同一批文件。

**画面构思**
- 一个发动机先单独展示，然后分别装进两辆不同的车里跑，计时牌上显示 42% 和 78%。
- 爆炸图：模型在中心，harness 的各个部件（工具、权限、规则文件、上下文管理、反馈）围成一圈。
- 自主程度画成一架梯子，六级逐级亮起；旁边一根"你亲自看的代码量"随着往上爬而下降，另一根"需要的检查和隔离"随之上升。

**来源**：Princeton HAL / Sayash Kapoor, 2025-12；RedAccess（via Security Boulevard）, 2026-05

### 第 7 章　工作流程（65 秒）

**要点**
1. 推荐顺序：
   1. 让它先读相关代码；
   2. 出计划；
   3. 你看计划、改计划；
   4. 再动手改代码；
   5. 验证；
   6. 提交。

   多数工具都有计划模式，课件里讲 Qoder 三种模式那页提到过。
2. 小步走：每完成一小步、验证通过，就 commit 一次。Git 的提交就是存档点，AI 改坏了直接回到上一个存档（呼应课件 Git 章节）。Anthropic 的官方指南也提到，git 记录和检查点能帮模型在多次会话之间接着干活。
3. 有风险的尝试，开一个分支来做。
4. 用测试当验收标准：先有测试，再让 AI 改到测试通过。它能自己跑测试，就能自己发现问题。但要防着它为了让测试通过而作弊，第 8 章讲。
5. 同一个问题失败三次就停下来，然后三选一：
   - 回退到上一个提交；
   - 补充信息后新开对话；
   - 自己写。
6. 什么时候不该用：还在学基础语法的时候。自己写不出来的代码，你也检查不出它错在哪。课程作业能不能用 AI、能用到什么程度，按老师的规定来。

**画面构思**
- 一条 Git 时间线，上面一个个存档点。AI 的修改出错时，时间线回到上一个存档点，错误的那段淡出。
- 一个失败计数器从 1 走到 3，到 3 时停下，出现三个选项。
- 六个步骤的流程条，"你看计划"这一步用不同颜色标出，表示这一步由人来做。

**来源**：Anthropic, *Prompting best practices*（关于 git 和状态跟踪的部分）

### 第 8 章　检查结果（65 秒）

**要点**
1. AI 说"完成了"之后要做三件事：
   - 看 diff，确认改了哪些行；
   - 自己运行一遍；
   - 测边界情况：空输入、超长输入、非法输入。
2. 常见的"看起来完成了"：
   - 把失败的测试注释掉或删掉；
   - 把测试期望的值直接写死在代码里；
   - 用 try-catch 把异常吞掉，不处理；
   - 留一句 TODO 就当实现了；
   - 没跑测试就说"全部通过"。

   Anthropic 的官方指南专门提醒过：模型可能会为了让测试通过而写死数值。
3. AI 会编造东西：不存在的方法、参数、配置项，以及不存在的依赖包。
   - 2026 年 4 月的一项研究发现，5 个主流模型会编出相同的 127 个不存在的包名，其中 53 个当时还没人注册。
   - 攻击者可以抢先注册这些名字，在里面放恶意代码，这叫 slopsquatting。
   - 装依赖之前，先去 Maven Central、npm 或 PyPI 确认这个包真实存在，再看看下载量和发布者。
4. 主观感觉不可靠。METR 2025 年做过一个对照实验：16 位熟练的开源开发者用 AI 之后，完成任务实际慢了 19%，他们自己却估计快了 20%。2026 年 2 月的更新测出快了约 18%，但 METR 自己说明这次样本有选择偏差，结果不可靠。这里要讲的不是"AI 让人变慢"，而是有没有变快要靠测量，不能靠感觉。

**画面构思**
- 测试列表里一个红色的失败项，被一行 `//` 悄悄注释掉，接着出现绿色对勾"全部通过"。然后镜头拉回 diff，把那行注释圈出来。
- 一个包名在注册表里搜索，结果为空；随后被一个陌生账号注册，包图标变成可疑的颜色。
- 两根柱子："自我感觉 +20%"和"实际测量 −19%"。

**来源**：Anthropic, *Prompting best practices*；Churilov, 2026-04（via InfoWorld）；METR, 2025-07 & 2026-02

### 第 9 章　安全和权限（75 秒）

**要点**
1. 密钥（API Key、数据库密码）不写进代码，不放进前端，不提交到 Git；放在 .env 文件里，并把 .env 加进 .gitignore。GitGuardian 2026 年的报告显示：
   - 2025 年公开 GitHub 上新泄露约 2865 万个密钥，比前一年多 34%；
   - AI 服务的密钥泄露增加了 81%；
   - Claude Code 参与的提交，密钥泄露率是 3.2%，全体提交的基线是 1.5%；
   - 2022 年泄露的有效密钥，到 2026 年 1 月仍有 64% 没有作废。
2. 代码本身也不安全。Veracode 2026 年测了 100 多个模型，生成的代码通过安全检查的比例约 56%，和前一年差不多。按语言看 Java 最低，约 30%，正好是这门课学的语言。
3. 不要在存着真实账号和密钥的环境里开"全部自动批准"。以 2026 年 4 月的 PocketOS 事故为例：
   - 经过：Cursor 里运行的 Agent，在一个无关文件里找到一个权限过大的 API Token，用它删掉了生产数据库。备份和数据存在同一个存储卷上，一起被删，丢失了三个月的客户数据。
   - 原因在人：Token 权限过大，放在 Agent 能读到的地方，Agent 直接连着生产环境，备份没有和数据分开存放。
4. 删除文件、强制推送、修改数据库这类命令，设置成必须手动确认。能在容器或沙箱里跑的，就在沙箱里跑。
5. 提示词注入：Agent 读到的网页、Issue、README、依赖文档里，可能藏着写给 AI 的指令。来源不明的 MCP 插件和扩展不要装。
6. 课件里讲过的"不发密码、Token、私钥和他人个人信息"，这里一句带过。

**画面构思**
- 一个文件里躺着一串 Token。Agent 读取后，Token 发光；然后数据库图标和旁边的备份图标一起碎掉。
- 一个仪表盘指针停在 56%；下方各语言的条形图里，Java 那根最短，并被高亮。
- 一个 `.env` 文件被放进 `.gitignore` 的"保险箱"，提交时被挡在外面。

**来源**：GitGuardian, *State of Secrets Sprawl 2026*；Veracode, *2026 GenAI Code Security Report*；TechCentral, 2026-04（PocketOS）

## 四、术语表（字幕第一次出现时用）

| 术语 | 一句话解释 |
|---|---|
| vibe coding | 只用自然语言让 AI 写代码，自己基本不看代码 |
| Agent（智能体） | 能自己调用工具、多轮行动直到完成任务的 AI |
| 上下文窗口 | 模型一次能看到的全部内容，有容量上限 |
| context rot | 输入越长，模型表现越不稳定的现象 |
| token | 模型计费和计算长度的单位，大约是一个词或一两个汉字 |
| 规则文件 | AGENTS.md、CLAUDE.md 等，每次对话自动带上的项目说明 |
| MCP | 让 AI 连接外部工具和数据的一种标准接口 |
| harness | 模型之外的全部：工具、权限、提示词、上下文管理、反馈等 |
| hooks | 在特定时机自动运行的脚本，比如每次改完代码自动跑检查 |
| 子代理 | 主 Agent 派出去处理子任务的另一个 Agent，用来分担上下文 |
| diff | 修改前后的逐行对比 |
| slopsquatting | 抢注 AI 编造出来的包名，在里面放恶意代码 |
| 提示词注入 | 在 AI 会读到的内容里藏指令，诱导它做别的事 |
